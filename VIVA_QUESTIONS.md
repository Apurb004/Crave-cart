### Section 1: Python & Flask Fundamentals

#### Q1: What is Flask and why was it chosen over Django for CraveCart?
**Answer**: Flask is a lightweight WSGI microframework for Python based on Werkzeug and Jinja2. Unlike Django, which is an opinionated "batteries-included" monolith with built-in ORM, admin, and forms, Flask gives developers full architectural control to assemble a modular structure. For CraveCart, Flask was selected because:
1. It supports the Application Factory pattern and Blueprints, facilitating clean domain separation (`auth`, `customer`, `admin`).
2. It avoids unnecessary framework bloat, resulting in faster startup, lower memory consumption, and clean code that is easy to explain and defend in an academic viva.

#### Q2: What is the WSGI specification and how does Flask implement it?
**Answer**: WSGI (Web Server Gateway Interface, PEP 3333) is a standard calling convention for web servers to forward requests to Python web applications. In Flask, the central application object (`app = Flask(__name__)`) is a WSGI-compliant callable. When an incoming HTTP request arrives at a WSGI server (like Werkzeug in development or Gunicorn/uWSGI in production), the server calls `app(environ, start_response)`. Flask parses the WSGI `environ` dictionary into a `Request` context object and outputs the HTTP response via `start_response`.

#### Q3: What is the Application Factory Pattern and why is it crucial in CraveCart?
**Answer**: The Application Factory pattern creates the Flask application instance inside a function (`create_app(config_name)`) rather than as a global singleton. In CraveCart (`app/__init__.py`), this pattern is crucial because:
1. It avoids circular import errors between routes, models, forms, and extension instances.
2. It allows running the application in different environments (Development, Testing, Production) with isolated configurations.
3. In unit testing (`tests/conftest.py`), each test case can instantiate a fresh application instance with an in-memory SQLite database, guaranteeing 100% test isolation.

#### Q4: What are Flask Application and Request Contexts?
**Answer**: Flask uses thread-local proxies to manage execution contexts without requiring explicit argument passing:
1. **Application Context (`current_app`, `g`)**: Tracks application-level data such as database connections, configuration variables, and custom CLI commands.
2. **Request Context (`request`, `session`)**: Tracks request-level data generated by the client, such as HTTP headers, query parameters (`request.args`), form data (`request.form`), cookies, and active session dictionaries.
Contexts are automatically pushed when an HTTP request enters Flask and popped when the response is generated.

#### Q5: What role do Flask extensions play and how are they bound?
**Answer**: Extensions provide additional modular capabilities. In CraveCart, extensions (`db = SQLAlchemy()`, `login_manager = LoginManager()`, `csrf = CSRFProtect()`) are instantiated globally in `app/extensions.py` without an active app object. Later, inside `create_app()`, they are bound to the concrete application instance via `extension.init_app(app)`. This two-phase initialization prevents circular dependencies.

### Section 2: Frontend & Architecture

#### Q6: Why did CraveCart use vanilla HTML5, CSS3, and ES6 JavaScript instead of React, Vue, or Angular?
**Answer**: 
1. **Zero Build Step & Lower Latency**: Vanilla web technologies require no bundlers (Webpack, Vite), node runtime dependencies, or transpilation pipelines. HTML is rendered directly on the server by Jinja2, yielding fast First Contentful Paint (FCP).
2. **SEO & Search Indexing**: Server-rendered HTML is immediately indexable by web crawlers without headless browser rendering.
3. **No State Synchronization Flaws**: Client-side frameworks often introduce state discrepancies between client memory and server databases. In CraveCart, every page render reflects real-time database stock and pricing.
4. **Academic Transparency**: The examiner can inspect standard HTML/CSS/JS without sifting through compiled minified bundles.

#### Q7: What is Jinja2 and how does template inheritance work in CraveCart?
**Answer**: Jinja2 is Flask's server-side templating engine. Template inheritance is achieved using `{% extends 'base.html' %}` and `{% block content %} ... {% endblock %}` tags. The master layout (`app/templates/base.html`) defines the global HTML document, meta tags, CSRF token, navbar, flash container, and footer. Child templates (such as `menu.html` or `checkout.html`) inherit this scaffold and only override specific content blocks, adhering to the DRY (Don't Repeat Yourself) principle.

#### Q8: What are Jinja2 Macros and Context Processors? Give examples from CraveCart.
**Answer**: 
- **Macro**: A reusable Jinja2 component analogous to a function. In CraveCart, `app/templates/components/_food_card.html` exports the macro `render_food_card(item)` to ensure dishes on the homepage, menu, and recommendations render with identical typography, image placeholders, price formatting, and "+ Add to Cart" buttons.
- **Context Processor**: A function registered with `@app.context_processor` that automatically injects global variables into all rendered templates. In CraveCart, `inject_global_template_variables()` injects `cart_count` (the number of items in the session cart) and `restaurant_tagline` across all pages.

### Section 3: HTTP Protocol & Network Operations

#### Q9: What is the difference between HTTP GET and POST methods in CraveCart?
**Answer**:
- **GET**: An idempotent, safe method used to retrieve resources without modifying server state. In CraveCart, `GET /`, `GET /menu`, and `GET /orders` retrieve HTML views. Query parameters (e.g., search keywords: `/menu?q=truffle`) are visible in the URL and can be bookmarked.
- **POST**: A non-idempotent method used to submit data that causes a change in server state. In CraveCart, user registration, login, cart item addition, order checkout, and status updates use `POST`. All mutating POST requests require a CSRF token.

#### Q10: What is the Post/Redirect/Get (PRG) pattern and where is it applied?
**Answer**: The Post/Redirect/Get pattern prevents duplicate form submissions caused by users clicking the browser's refresh button. In CraveCart, when a customer places an order (`POST /checkout`), the server commits the order and returns an `HTTP 302 Redirect` to `GET /orders/confirmation/<id>`. If the customer refreshes the confirmation page, only the safe GET request is re-executed, preventing duplicate orders.

#### Q11: What are HTTP status codes and which ones are actively used in CraveCart?
**Answer**:
- `200 OK`: Request succeeded (e.g., viewing menu or cart).
- `302 Found`: Temporary redirect (e.g., after login, registration, or adding to cart).
- `400 Bad Request`: Form validation failure or malformed input.
- `403 Forbidden`: Authenticated user lacks permission (e.g., customer attempting to view `/admin/*` or another customer's order).
- `404 Not Found`: Target entity or route does not exist.
- `500 Internal Server Error`: Unhandled server-side exception.

#### Q12: How does CraveCart handle AJAX / Fetch requests with CSRF protection?
**Answer**: In `app/templates/base.html`, a `<meta name="csrf-token" content="{{ csrf_token() }}">` tag is provided in the document `<head>`. JavaScript asynchronous requests (e.g., cart mutations) extract this token and attach it to the `X-CSRFToken` HTTP header, satisfying Flask-WTF validation.

### Section 4: Routing & Application Architecture

#### Q13: What is a Flask Blueprint?
**Answer**: A Blueprint is a way to organize related routes, handlers, and templates into modular components. Rather than registering routes directly onto the global `app`, routes are attached to a Blueprint. In CraveCart:
- `auth_bp` (`/auth` prefix): Registration, login, logout.
- `customer_bp` (`/` prefix): Homepage, menu catalog, cart, checkout, order history.
- `admin_bp` (`/admin` prefix): Dashboard, category CRUD, food item CRUD, order fulfillment.
All three blueprints are registered with the application in `app/__init__.py`.

#### Q14: How does dynamic URL routing work in Flask?
**Answer**: Dynamic routes contain variable converters enclosed in angle brackets. For example, `@customer_bp.route('/food/<int:item_id>')` matches requests like `/food/3`, casts `3` to an integer, and passes it as `item_id` to the view function. If a client accesses `/food/abc`, Flask automatically returns a 404 because the parameter fails the integer converter.

#### Q15: What is `url_for()` and why is it preferred over hardcoded URLs?
**Answer**: `url_for('customer.food_detail', item_id=item.id)` generates URLs based on the endpoint name rather than a hardcoded string (`/food/5`). Benefits:
1. If the route URL changes (e.g., from `/food/<id>` to `/dishes/<id>`), template and view code remains unchanged.
2. It automatically handles URL encoding of special characters.
3. It handles root deployment paths or reverse-proxy prefixes transparently.

#### Q16: How are 403, 404, and 500 error handlers implemented?
**Answer**: Custom error handlers are registered in `app/__init__.py` using `@app.errorhandler(403)`, `@app.errorhandler(404)`, and `@app.errorhandler(500)`. They render dedicated, styled templates located in `app/templates/errors/` with helpful return buttons, ensuring customers never see raw server tracebacks or generic browser error screens.

### Section 5: Authentication & Authorization

#### Q17: What is the difference between Authentication and Authorization?
**Answer**:
- **Authentication (AuthN)**: Verifying the identity of the user ("Who are you?"). E.g., validating email and password credentials at `/auth/login`.
- **Authorization (AuthZ)**: Verifying permissions to access specific resources ("What are you allowed to do?"). E.g., restricting `/admin/*` to users with `role == 'admin'`, or allowing customers to only view their own orders.

#### Q18: How are passwords stored securely in CraveCart?
**Answer**: Passwords are never stored in plaintext. CraveCart uses Werkzeug's `generate_password_hash()` and `check_password_hash()` utilities. When a customer registers, the password is processed using a salted PBKDF2 (Password-Based Key Derivation Function 2) algorithm with SHA-256 and thousands of hashing iterations. `check_password_hash` uses timing-safe comparisons to prevent timing attacks.

#### Q19: How does Flask-Login manage user sessions?
**Answer**: Flask-Login tracks authenticated users across HTTP requests via an encrypted session cookie:
1. `login_user(user)` stores the user's primary key (`user.id`) in the session.
2. The user loader callback (`@login_manager.user_loader`) queries the database using `db.session.get(User, int(user_id))` to reconstruct `current_user` on subsequent requests.
3. `current_user.is_authenticated` allows checking login state in any template or view function.
4. `logout_user()` removes the user ID from the session.

#### Q20: How is Role-Based Access Control (RBAC) enforced in CraveCart?
**Answer**: CraveCart implements a custom Python decorator `@admin_required` (`app/utils/decorators.py`):
```python
def admin_required(f):
    @wraps(f)
    def decorated_function(*args, **kwargs):
        if not current_user.is_authenticated:
            return redirect(url_for('auth.login', next=request.url))
        if not current_user.is_admin:
            abort(403)
        return f(*args, **kwargs)
    return decorated_function
```
Applying `@admin_required` above any admin view ensures unauthorized customers receive `HTTP 403 Forbidden` and anonymous visitors are redirected to `/auth/login`.

### Section 6: Session Management & State

#### Q21: What is a Flask session and how does it differ from a server-side session?
**Answer**: By default, Flask uses cryptographically signed client-side cookies for session storage. The session dictionary is serialized (JSON), compressed, and signed with the application's `SECRET_KEY` using HMAC-SHA256. 
- The client cannot tamper with session data (e.g., modify user ID or cart items) without invalidating the cryptographic signature.
- Unlike server-side sessions (e.g., Redis), client-side sessions require no external cache database, simplifying deployment.

#### Q22: How is the shopping cart structured inside the session?
**Answer**: The cart is stored in `session['cart']` as a dictionary mapping food item string IDs to integer quantities:
```json
{
  "3": 2,
  "7": 1
}
```
String keys are required because JSON dictionary keys must be strings. `CartService` converts these keys to integers, reconciles them against active database records, and recalculates all line subtotals and totals on the server.

#### Q23: Why is `session.modified = True` required when mutating the cart?
**Answer**: Flask only tracks top-level assignments to the `session` object (e.g., `session['cart'] = ...`). When mutating a nested dictionary (e.g., `session['cart']['3'] = 2` or `del session['cart']['3']`), Flask's session object may not detect the change. Setting `session.modified = True` explicitly marks the session as dirty, ensuring the updated cookie is sent in the HTTP response headers.

#### Q24: What happens if an item in the session cart is deleted or marked out of stock by an admin before checkout?
**Answer**: During every cart review (`/cart`) and checkout attempt (`/checkout`), `CartService.get_cart_details()` checks active database records:
1. If a dish was marked `is_available = False`, `has_unavailable` is set to `True`.
2. The UI displays an alert: *"Notice: One or more dishes in your cart are currently sold out."*
3. The checkout button is disabled until the customer removes the unavailable dish.
4. If a dish was deleted from the database, it is automatically filtered out of the reconciliation map.

### Section 7: SQL & SQLite

#### Q25: Why was SQLite selected for this single-restaurant project?
**Answer**:
1. **Zero Configuration**: SQLite is an embedded, file-based database requiring no standalone server daemon, user permission setup, or socket configuration.
2. **ACID Compliant**: Provides full Atomic, Consistent, Isolated, and Durable transactions.
3. **Single-Process Reliability**: For a single restaurant handling local dining orders, SQLite easily handles thousands of reads per second and serializes write transactions safely.
4. **Portability**: The entire database lives in `instance/cravecart.db`, making backups, demonstrations, and test execution trivial.

#### Q26: Are SQLite foreign keys enabled by default, and how does CraveCart handle them?
**Answer**: No. SQLite disables foreign key enforcement by default for backwards compatibility. In CraveCart (`app/__init__.py`), foreign key enforcement is explicitly activated using an engine event listener:
```python
from sqlalchemy import event
from sqlalchemy.engine import Engine

@event.listens_for(Engine, "connect")
def set_sqlite_pragma(dbapi_connection, connection_record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA foreign_keys=ON")
    cursor.close()
```
This ensures cascade deletes and foreign key restrictions are strictly enforced by the database engine.

#### Q27: What is database normalization and what normal form does CraveCart achieve?
**Answer**: Normalization is the process of structuring relational tables to reduce redundancy and avoid insertion, update, and deletion anomalies. CraveCart achieves **Third Normal Form (3NF)**:
1. **1NF**: All columns contain atomic values; each record has a unique primary key.
2. **2NF**: Achieves 1NF, and all non-key attributes are fully functional-dependent on the primary key (no partial dependencies).
3. **3NF**: Achieves 2NF, and no non-key attribute is transitively dependent on another non-key attribute (e.g., category details are separated into the `categories` table rather than duplicated in `food_items`).

#### Q28: What is SQL Injection and how does CraveCart prevent it?
**Answer**: SQL Injection occurs when untrusted user input is concatenated directly into a raw SQL query string (e.g., `SELECT * FROM users WHERE email = '` + input + `'`), allowing attackers to alter the query logic. CraveCart prevents SQL injection by using **SQLAlchemy ORM**, which uses parameterized queries and prepared statements exclusively. User inputs are passed as bound parameters, never as executable SQL code.

### Section 8: Object-Relational Mapping (ORM) & SQLAlchemy

#### Q29: What is an ORM and what are its advantages?
**Answer**: An Object-Relational Mapper (ORM) maps database tables to Python classes and rows to Python objects. Advantages:
1. Developers interact with Python objects and methods rather than writing raw SQL.
2. Database abstraction: Switching from SQLite to PostgreSQL or MySQL requires only changing the connection string in `.env`.
3. Automatic schema generation (`db.create_all()`).
4. Automated parameterization and object caching.

#### Q30: What is the difference between `db.session.add()`, `db.session.flush()`, and `db.session.commit()`?
**Answer**:
- `db.session.add(obj)`: Stages the object in SQLAlchemy's identity map. No SQL is sent to the database yet.
- `db.session.flush()`: Sends the SQL `INSERT`/`UPDATE` statements to the database transaction, allowing the database to generate primary keys (`obj.id`), but does not commit the transaction.
- `db.session.commit()`: Permanently writes all flushed changes to disk and ends the transaction. If an exception occurs, `db.session.rollback()` reverts all staged modifications.

#### Q31: How does SQLAlchemy 2.0+ differ from legacy 1.x in querying?
**Answer**: In SQLAlchemy 1.x, queries were often executed via `Model.query.filter_by().all()` or `Model.query.get(id)`. In SQLAlchemy 2.0+, `db.session.get(Model, id)` or `db.get_or_404(Model, id)` is preferred for primary key lookups, and `db.select(Model).where(...)` is used for queries. CraveCart uses the 2.0-compliant methods.

#### Q32: What is the `back_populates` parameter in SQLAlchemy relationships?
**Answer**: `back_populates` establishes a bidirectional relationship between two models. For example, in `Order`, `items = db.relationship('OrderItem', back_populates='order')` and in `OrderItem`, `order = db.relationship('Order', back_populates='items')`. When an `OrderItem` is appended to `order.items`, SQLAlchemy synchronizes both sides of the relationship in memory.

### Section 9: Database Relationships

#### Q33: How is the One-to-Many relationship between User and Order implemented?
**Answer**: 
1. In the `orders` table, `user_id = db.Column(db.Integer, db.ForeignKey('users.id'), nullable=False)`.
2. In the `User` model, `orders = db.relationship('Order', back_populates='user', lazy='dynamic')`.
This allows calling `user.orders.all()` to fetch all orders placed by that customer.

#### Q34: What is Cascade Delete and where is it used in CraveCart?
**Answer**: Cascade delete ensures that when a parent record is deleted, all dependent child records are automatically deleted by the database. In CraveCart:
`items = db.relationship('OrderItem', back_populates='order', cascade='all, delete-orphan')`
If an `Order` record is deleted, all associated `OrderItem` snapshot rows are removed, preventing orphan records.

#### Q35: Why is Cascade Delete NOT applied between Category and FoodItem?
**Answer**: Deleting a category should never silently delete all dishes in that category. Instead, CraveCart enforces a relational safety check: if an administrator attempts to delete a category that still contains dishes, the operation is blocked and an error alert is shown: *"Cannot delete category because it still contains N dishes."* The admin must reassign or remove the dishes first.

#### Q36: Why does `OrderItem` use a nullable `food_item_id` foreign key?
**Answer**: In `OrderItem`, `food_item_id = db.Column(db.Integer, db.ForeignKey('food_items.id'), nullable=True)`. If a restaurant permanently removes a seasonal dish from its catalog (`food_items`), past customer order receipts must not break or fail foreign key constraints. The item's details remain safe inside `OrderItem.item_name` and `OrderItem.unit_price`.

### Section 10: CRUD & Safe Operations

#### Q37: What does CRUD stand for and how is it implemented for menu dishes?
**Answer**: CRUD stands for Create, Read, Update, Delete:
1. **Create**: Admin accesses `/admin/items/new`, submits `FoodItemForm`, and `db.session.add(dish)` inserts the row.
2. **Read**: Customers view dishes on `/` and `/menu`; admins inspect inventory on `/admin/items`.
3. **Update**: Admin edits price, name, or description on `/admin/items/<id>/edit`, or toggles availability on `/admin/items/<id>/toggle-stock`.
4. **Delete**: Admin submits `/admin/items/<id>/delete` via POST, removing the item from the catalog.

#### Q38: How is the category safe-deletion check implemented in the backend?
**Answer**: In `app/admin/routes.py`:
```python
@admin_bp.route('/categories/<int:cat_id>/delete', methods=['POST'])
@admin_required
def category_delete(cat_id: int):
    category = db.get_or_404(Category, cat_id)
    dish_count = FoodItem.query.filter_by(category_id=category.id).count()
    if dish_count > 0:
        flash(f'Cannot delete category "{category.name}" because it still contains {dish_count} dishes.', 'danger')
        return redirect(url_for('admin.categories'))
    db.session.delete(category)
    db.session.commit()
    flash(f'Category "{category.name}" was successfully deleted.', 'success')
    return redirect(url_for('admin.categories'))
```

#### Q39: How does the quick stock availability toggle work?
**Answer**: The admin dish table includes an interactive stock status button submitting to `/admin/items/<id>/toggle-stock`. The view function negates `dish.is_available = not dish.is_available` and commits. The change takes effect across the customer storefront and cart reconciliation.

#### Q40: How are images handled when an external URL is invalid or omitted?
**Answer**: All `<img>` tags for dishes include an `onerror` fallback:
```html
<img src="{{ item.image_url or url_for('static', filename='images/food-placeholder.svg') }}"
     alt="{{ item.name }}"
     onerror="this.onerror=null; this.src='/static/images/food-placeholder.svg';">
```
If an image fails to load or the URL is missing, it falls back to CraveCart's custom vector SVG placeholder.

### Section 11: Order Processing & State Machine

#### Q41: Walk through the complete order creation transaction step by step.
**Answer**:
1. The customer submits delivery coordinates via `POST /checkout`.
2. Flask-WTF validates recipient name, phone format, and delivery address.
3. `CartService.get_cart_details(session['cart'])` calculates verified totals from database records and verifies all items are in stock.
4. An `Order` record is instantiated with `status='PLACED'`, `payment_method='CASH ON DELIVERY'`, and total amount.
5. `OrderService` creates corresponding `OrderItem` records with snapshot prices and names.
6. The entire batch is committed atomically inside `db.session.commit()`. If an error occurs, `db.session.rollback()` reverts everything.
7. Only after a confirmed commit is the session cart emptied via `session.pop('cart', None)`.
8. The customer is redirected to the order confirmation page.

#### Q42: What is an atomic database transaction and why is it essential for orders?
**Answer**: An atomic transaction adheres to the "all-or-nothing" principle. Placing an order requires inserting one `Order` row and multiple `OrderItem` rows. If the server were to crash or encounter a constraint failure midway through inserting line items, committing partially would result in a corrupt order with missing dishes. Wrapping all inserts in a single transaction guarantees the database is never left in a partial state.

#### Q43: How is the order fulfillment finite-state machine enforced in CraveCart?
**Answer**: The `Order` model implements state machine validation methods:
```python
VALID_TRANSITIONS = {
    'PLACED': ['CONFIRMED', 'CANCELLED'],
    'CONFIRMED': ['PREPARING', 'CANCELLED'],
    'PREPARING': ['OUT FOR DELIVERY'],
    'OUT FOR DELIVERY': ['DELIVERED'],
    'DELIVERED': [],
    'CANCELLED': []
}

def can_transition_to(self, target_status: str) -> bool:
    return target_status in self.VALID_TRANSITIONS.get(self.status, [])
```
When an admin submits a status change at `/admin/orders/<id>/status`, the backend calls `order.can_transition_to(target_status)`. Invalid transitions (e.g., trying to jump from `PLACED` to `DELIVERED`) are rejected with a warning.

#### Q44: What are the rules regarding order cancellation?
**Answer**: Customers can cancel an order self-service **only while its status is `PLACED`**. Once an administrator confirms the order (`CONFIRMED`), kitchen preparation has commenced and the customer cancel button disappears. Only administrators can cancel a confirmed order under exceptional circumstances.

### Section 12: Security Best Practices

#### Q45: What is Cross-Site Request Forgery (CSRF) and how does CraveCart protect against it?
**Answer**: CSRF occurs when a malicious website tricks a user's browser into executing an unauthorized action on a site where the user is authenticated. CraveCart prevents CSRF using **Flask-WTF**:
1. Every user session is assigned a unique cryptographic CSRF token.
2. All POST forms render `{{ form.hidden_tag() }}` or `<input type="hidden" name="csrf_token" value="{{ csrf_token() }}">`.
3. When the form is submitted, Flask-WTF verifies that the submitted token matches the session token. Requests lacking a valid token are rejected with `HTTP 400 Bad Request`.

#### Q46: Why should client-submitted prices or totals never be trusted?
**Answer**: Any data originating from the client browser can be modified via browser Developer Tools, proxy software (Burp Suite), or script commands. If an application calculates the total on the frontend and sends `total_amount=1.00`, a customer could purchase expensive meals for pennies. CraveCart ignores all prices and subtotals sent by the client. It only accepts the dish ID and quantity, looking up prices directly from the SQLite database.

#### Q47: How does CraveCart protect against Insecure Direct Object References (IDOR)?
**Answer**: IDOR occurs when an application exposes a reference to an internal database object (e.g., `/orders/5`) without verifying that the requesting user owns that object. In `app/customer/routes.py`:
```python
order = db.get_or_404(Order, order_id)
if order.user_id != current_user.id and not current_user.is_admin:
    abort(403)
```
If Customer A tries to view Customer B's order by changing the ID in the URL, Flask aborts with `HTTP 403 Forbidden`.

#### Q48: How does CraveCart prevent Open Redirect attacks?
**Answer**: An open redirect occurs when an application redirects to a user-supplied URL parameter (e.g., `/auth/login?next=https://evil.com`) without validation. CraveCart implements an `is_safe_url()` utility (`app/utils/decorators.py`) using `urlsplit()`. It checks that the `next` target is relative or matches the application's host, falling back to `/` if an external domain is detected.

### Section 13: Project-Specific Architecture Decisions

#### Q49: Why was Cash on Delivery (COD) chosen over a simulated payment gateway?
**Answer**:
1. **Realism**: Integrating a sandbox credit card form with fake inputs does not represent real payment gateway architecture (which requires webhooks, idempotency keys, and merchant accounts).
2. **Frictionless Experience**: For a local restaurant, Cash on Delivery is an authentic, high-conversion payment modality.
3. **Architectural Focus**: It allowed focusing engineering effort on core fundamentals: transactional integrity, price snapshotting, stock reconciliation, and state machines.

#### Q50: How is gross revenue calculated on the admin dashboard?
**Answer**: Revenue is calculated strictly from orders with status `DELIVERED`. Orders in `PLACED`, `PREPARING`, `OUT FOR DELIVERY`, or `CANCELLED` are excluded because cash has not yet been collected. The aggregation is executed using SQLAlchemy's `func.sum()` over `Order.total_amount` where `status == 'DELIVERED'`.

#### Q51: How does CraveCart guarantee mobile responsiveness without Bootstrap or Tailwind?
**Answer**: CraveCart uses modern CSS3 standards:
1. **CSS Custom Properties (Variables)**: Centralizes design tokens (`--color-primary-dark`, `--radius-lg`, `--shadow-card`).
2. **CSS Grid & Flexbox**: Used for layout structures. Grid components use `repeat(auto-fill, minmax(280px, 1fr))` for automatic column wrapping.
3. **Media Queries**: Specific breakpoints at 992px, 768px, and 480px adapt table wrappers, collapse sidebars into mobile drawers, and scale down typography.

#### Q52: How did automated testing contribute to the quality of CraveCart?
**Answer**: CraveCart includes 36 automated tests running under `pytest`. The test suite covers:
1. Unit tests for password hashing and role assignments.
2. Route tests for public views and error handling.
3. Form validation tests for duplicate emails and password mismatch.
4. Security tests verifying RBAC and IDOR blocks.
5. Transactional tests verifying price recalculation and snapshot preservation.
6. A complete 14-step end-to-end integration test simulating the entire user lifecycle.
Running `pytest` provides confidence that modifications do not introduce regressions.
